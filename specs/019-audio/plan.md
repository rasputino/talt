# Implementation Plan: Audio

**Branch**: `019-audio` | **Date**: 2026-11-23 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/019-audio/spec.md`

## Summary

Add an audio layer to `Talt.Client`: a small client-only audio system that plays interface clicks,
command feedback, construction sounds, a camera-driven ambience bed, eight positional vehicle
engines and an original streamed music playlist, mixed through master, music, effects and ambient
buses controlled from the existing Settings screen and persisted in `PlayerSettings`.

The native backend is **miniaudio** (0.11.26) through the **JAJ.Packages.MiniAudioEx** NuGet package
(MIT / Unlicense). Audio never enters `Talt.Core`: the client reads simulation events
(`CommandProcessed`, day/month/year events), the current camera and the vehicle snapshot, and turns
them into audio cues. A pure managed mixer (gain curves, voice budget, playlist, ambience selection)
is unit-testable without a device; the native backend is a thin adapter hidden behind two small
interfaces and falls back to silence when initialization fails. All sounds and music are original
synthesized works generated by a committed tool and listed in `README.md`.

## Technical Context

**Language/Version**: C# latest on .NET 10 (nullable enabled, warnings as errors).

**Primary Dependencies**: `JAJ.Packages.MiniAudioEx` 4.0.1 (managed wrapper, miniaudio 0.11.26
native binaries for win-x64/win-arm64, linux-x64/linux-arm64, osx-x64/osx-arm64; MIT / Unlicense).
Asset generation only: `EggEncoder` 4.114.5 (MIT, file-based tool, not referenced by the game).

**Storage**: audio settings in the existing `PlayerSettings` JSON file; cues, bus assignments,
voice budget and the music playlist in an embedded validated data file
(`src/Talt.Client/Audio/Data/audio.json`); audio assets copied to the output folder under `audio/`.

**Testing**: xUnit in `tests/Talt.Client.Tests/Audio` with a fake backend; no test opens a real
audio device. BenchmarkDotNet benchmark in `benchmarks/Talt.Benchmarks` for the per-frame mixer.

**Target Platform**: Windows, Linux and macOS, x64 and arm64, with or without an audio device.

**Project Type**: desktop game client (one application project plus existing tests and tools).

**Performance Goals**: audio update < 0.5 ms CPU per frame on the reference hardware, zero managed
allocations per frame in steady state, no frame-loop blocking, 8 vehicle voices maximum.

**Constraints**: no audio references in `Talt.Core`; no change to simulation results, saves,
replays or fingerprints; silent and non-fatal without a device; all player text localized in
English and Spanish; all shipped audio original or commercially licensed; volume sliders must be
focusable and adjustable with the arrow keys.

**Scale/Scope**: 20 000–50 000 moving vehicles in the reference scenario; 8 simultaneous vehicle
engines, 4 one-shots, 2 ambience beds and 1 music stream; at least 2 original music tracks;
10 audio files (5 effects including the engine loop, 3 ambience and 2 music).

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Gate | Result |
|---|---|---|
| I. Core/Client separation | Audio code and the native package live only in `Talt.Client`; `Talt.Core` gains no audio reference; `tools/Talt.Headless` remains audio-free. | PASS |

| VII. Data-driven content | Cue definitions, bus assignment, gains, voice budget, ambience and playlist live in `Audio/Data/audio.json`, validated at load with clear errors. | PASS |

**Structure Decision**: one new `Audio` folder inside `Talt.Client` plus a small, isolated set of
hook edits in existing files. New logic and tests live in new files so the merge with features 006
and 009 (which touch `GameWindow.cs`, the HUD and `PlayerSettings.cs` in parallel) stays small.

## Post-Design Constitution Check

The design keeps the native boundary in one file, uses the existing embedded-data loader pattern,
adds tests that do not open a device, and does not touch `Talt.Core`. All gates still pass.

## Complexity Tracking

No violations. The native backend is the minimum needed to produce sound on three platforms; the
alternative of writing per-platform audio backends was rejected as more code, more risk and more
maintenance.
